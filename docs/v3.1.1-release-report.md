# V3.1.1 Hardening Release Report

Date: 2026-08-28. Base: V3.1 commit `5a75f5021c47ebd4a57c001196ac3fd718ec389c`.
This report describes only the `v3.1.1-hardening` branch. `main`, `v1`, `v2`,
`v3`, and `v3.1` are preserved and are not rewritten or merged.

## What changed

- Manifest hashes are LF-normalized and include only release-controlled source;
  generated benchmark runs, temporary state, caches, and release metadata are
  excluded. The smoke execution result is CI-only; `check_smoke.py` rejects a
  result whose `skill_commit` differs from the tested `git rev-parse HEAD`.
- The release manifest separates source version/commit, generation time,
  deterministic tests, hosted CI, model behavior, E2E status, and limitations.
  The source commit is publisher-injected because a file cannot hash itself.
- `smoke_run.py` executes a public local fixture, records a real execution
  record and hashes, performs literature identity and region support checks,
  plans an experiment, creates node-specific anchors, validates the graph event
  chain, rebuilds the projection, and runs a harness self-test. It does not
  force graph nodes to PASS or claim a scientific result.
- `privacy_lint.py` and `sanitize_artifact.py` prevent local paths, credentials,
  tokens, and private review markers from public artifacts.
- Capability resolution now accepts purpose, load-bearing status, and
  criticality. `PROVISIONAL` is advisory-only. A `SPECIALIST` needs an exact
  pin, a relevant passed behavior trial, permissions, and activation scope
  before formal evidence work. Resolution remains distinct from execution;
  `handoff_runtime.py` validates the host handoff and checker contract.
- Evidence has `DECLARED`, `OBSERVED`, and `VERIFIED` levels. Observed/formal
  anchors require an execution or acquisition record; exit status and output
  hashes come from the runtime, not a user assertion. Legacy anchors with
  `status=VERIFIED` but no provenance level migrate to `DECLARED` with
  `legacy_status=VERIFIED` and cannot support a formal PASS. Git commits and
  content hashes are checked.
- Literature support records a retrieval ID, method, URI, retrieval time,
  materialized artifact hash, inspected region, region hash, inspection actor,
  and independent checker. A claim relation without retrieval is only recorded;
  snippet or abstract-only support is conditional. Method routing returns
  `UNRESOLVED` on zero reliable matches and exposes ambiguity and specialist
  escalation.
- Experiment ranking is qualitative by default and retains why/claim/threat
  decision records; fake decimal precision is rejected.

## Final consistency answers

- Does the E2E command actually generate the recorded output artifact? **Yes.**
  The fixture receives the output path, writes it itself, and the recorder
  stores its post-command hash and modification time.
- Can a pre-existing file be falsely claimed as execution output? **No.**
  Undeclared pre-existing outputs are rejected before command execution; inputs
  explicitly marked as pre-existing are recorded separately and never as
  produced outputs.
- How are legacy VERIFIED anchors migrated? **To `DECLARED`**, retaining
  `legacy_status=VERIFIED` and `migration_state=LEGACY_DECLARED`.
- Can legacy VERIFIED directly support formal evidence? **No.** Formal node
  contracts use effective provenance and reject legacy declarations.
- What exact conditions create OBSERVED? A command or acquisition must execute
  or read the artifact successfully, with a recorded command/acquisition,
  timestamps, exit status, and runtime hashes.
- What exact conditions create VERIFIED? An observed record and produced output
  must be rechecked by an independent checker with output, input/configuration,
  and code-version evidence.
- Does CLAIM_RELATION_VERIFIED require a retrieval record? **Yes**, including a
  materialized artifact and source hash.
- Is exact_region actually validated? **Yes** for local text artifacts; `line N`
  and `lines N-M` must exist and the region hash is stored.
- Can a committed benchmark silently reference an old commit? **No.** Runtime
  results are not committed, and release validation rejects the legacy result
  path if it reappears.
- What remains NOT_RUN? Only the authorized model behavior evaluation; the
  deterministic harness is not relabeled as a model evaluation.
