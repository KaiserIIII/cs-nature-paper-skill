## Qualification and security policy

The provider record uses three independent states:

- `qualification_status`: `UNAUDITED`, `AUDITED`, `PROVISIONAL`, `QUALIFIED`,
  `REJECTED`;
- `comparison_decision`: `NOT_RUN`, `INTERNAL_BETTER`, `EXTERNAL_BETTER`,
  `COMPLEMENTARY`, `EQUIVALENT`, `INCONCLUSIVE`;
- `eligibility`: `DISCOVERY_ONLY`, `ADVISORY_ONLY`, `NON_LOAD_BEARING`,
  `FORMAL_ELIGIBLE`, `DISABLED`.

`eligibility` is derived, never hand-promoted. Formal eligibility requires an
exact pin and source hash, acceptable license/security decisions, behavior
qualification, a typed output contract, an independent checker, and either
`EXTERNAL_BETTER` or verified `COMPLEMENTARY` value against `PUBLIC_CORE`.

Utility and security are also separate. Security checks include arbitrary shell,
package installation, runtime clone/download, secret access, credential
leakage, uncontrolled network, data egress, file writes/destructive behavior,
hidden telemetry, and subprocess scope. A useful provider with an unsafe
runtime remains ineligible.

## Accepted design deltas

The V4.1 design now records:

1. Discovery / Evaluation, System Adapter, and Reference / Methodology tiers.
2. The exact three-state provider model above.
3. SkillLens-derived benchmark metadata: run ID, timestamps, provider/V4/source
   hashes, model and prompt/config hashes, toolset/network policy, budgets,
   sampling/seed metadata, retries, artifacts, checker/judge identities and
   config hashes, failures, duration, and multiple rollouts where practical.
4. Dedicated `review-synthesis-provider`/process output followed by an
   independent `review-synthesis-checker` that validates but never generates,
   repairs, or rewrites the artifact it checks.
5. Native, profile-aware `falsification_obligation` rather than a POPPER
   runtime import.
6. Offline `PUBLIC_CORE` fallback and fail-closed behavior for missing,
   stale, unsafe, unlicensed, or behavior-unqualified candidates.

## Phase-1 and Phase-2 implementation status

The first executable contract slice is implemented in the isolated branch under
TDD:

- `scripts/v41_provider_contracts.py` ignores caller-authored qualification
  state for routing. It derives the three provider states from fixed-path,
  trust-root-loaded registry metadata, source-bound validation artifacts, and
  an independent checker artifact. The shipped qualification bundle is empty
  and `PENDING_FINAL_REVIEW`, so every external provider falls back to
  `PUBLIC_CORE`.
- `scripts/review_synthesis.py` produces synthesis artifacts and
  `scripts/review_synthesis_checker.py` independently validates them. The
  checker reconstructs the full canonical findings projection and enforces
  mutually distinct reviewer, synthesis-producer, and checker identities.
- Their JSON schemas and focused regression tests are present.
- `scripts/publication_profiles.py` deterministically resolves scoped layers in
  the required specificity order, records canonical hashes, and fails closed on
  category conflicts, invalid N/A assignments, ambiguous overrides, and stale
  source bindings.
- `scripts/falsification_obligation.py` derives profile-aware obligations for
  load-bearing or high-strength claims. The formal
  `derive_project_obligation` / `check_project_obligation` path loads the claim
  and profile inside the V4 project control-plane boundary, binds the three
  selected state files to `authority_snapshot_hash`, and requires a distinct
  checker. The lower-level `check_obligation` entry rejects caller-supplied
  `trusted_claim`, `trusted_profile`, and constructed context with
  `UNTRUSTED_CHECK_CONTEXT`. No result can change claim, evidence, graph, or
  publication state.
- `scripts/publication_sufficiency.py` consumes only a resolver artifact that
  replays exactly against the shipped authoritative profile registry, while
  preserving the fixed V4 depth dimensions as the default fallback.
- Schemas, templates, a conservative profile registry, and focused red-green
  regression tests are present for both Phase-2 contracts.
- `scripts/release_trust.py` verifies the fixed
  `assets/trust/v41_release_trust.json` anchor, its exact allowlist, three
  security-critical registry/qualification digests, and conservative release
  state. Neither callers nor runtime configuration can substitute another root.

The V4.1 blocker audit verifies that malformed public inputs return structured
rejections and that the release validator validates both V4.1 templates with
exact `oneOf` and type-sensitive `const` semantics. The original reviewer
payload is preserved verbatim at
`tests/fixtures/v41_original_reviewer_attack.py`; its baseline obligation hash
is `sha256:88c03979b0a94f057f0934616565405daf4fdf959c556a7820483f4593dce625`,
and the formerly accepted empty-claim-ID rewrite hash is
`sha256:33bd2ecdf3988dcae452872be8bb61584b9298b31c0ceb42859ddf5c425cbd07`.
The unchanged legacy call shape now fails closed with
`UNTRUSTED_CHECK_CONTEXT`. The formal replay at
`tests/fixtures/v41_formal_reviewer_replay.py` produces a verified baseline and
rejects nonempty `claim_id`, `claim_hash`, `profile_hash`, another real claim,
caller-named trusted context, and stale-snapshot attacks.

P0 disposition on this working tree:

- **P0-1 — implementation covered, pending final independent review.** The
  release trust record is independent of `SHA256SUMS.txt`, fixed to an exact
  allowlist, and pinned by a reviewed digest in the verifier. The original joint
  registry/manifest/provenance rewrite now returns `OBLIGATION_REJECTED`, and a
  direct registry plus matching `SHA256SUMS.txt` rewrite makes release-trust
  validation fail. Trust-root rotation requires an explicit verifier-anchor
  code change. This does not claim protection if an attacker can replace the
  verifier and reviewed anchor together.
- **P0-2 — implementation covered.** Non-mapping claim, profile, artifact,
  evidence, reviewer-report, and packet-check inputs return structured rejection
  at their public runtime entries.
- **P0-3 — implementation covered.** Both V4.1 contract templates are release
  inventory members; missing, malformed, schema-valid tampering, and manifest
  drift are exercised through `validate_release.validate()`.
- **P0-4 — implementation covered.** The release entry enforces exactly-one
  `oneOf` and JSON-type-sensitive `const`, including `false` versus `0`.
- **P0-5 — implementation covered, pending final independent review.** Only the project entry can
  reach the internal verifier, and its claim/profile are loaded from the V4
  state plus release-trust- and manifest-checked registry. This is a control-plane authority
  boundary, not a cryptographic claim that local state files survive arbitrary
  repository or validator compromise.

Reviewer-synthesis and provider-qualification disposition:

- Removing grouped synthesis findings and recomputing `synthesis_hash` is
  rejected because the independent checker rebuilds and compares the complete
  projection from frozen reviewer reports.
- Reviewer producers, synthesis producer, and synthesis checker cannot share an
  identity; unavailable isolation remains `SYNTHESIS_CONDITIONAL`.
- Caller-supplied `QUALIFIED`, `PASS`, `EXTERNAL_BETTER`, and
  `FORMAL_ELIGIBLE` values never authorize routing. A qualifying comparison must
  carry pinned source identity, counterbalanced run IDs, candidate and
  PUBLIC_CORE output hashes, judge/config identity, artifact-manifest hash, and
  an independently checked evidence-set hash.
- No shipped provider has such a bundle. External provider qualification is
  `PENDING_FINAL_REVIEW`, not PASS.

This does not claim that external providers are behavior-qualified, that any
adapter is formally eligible, or that V4.1 is released. Hosted CI and real
behavior qualification remain unproven. `release_status` remains
`RC_NOT_RELEASED` and `recommended_merge` remains `NO` until those release gates
are independently satisfied.
